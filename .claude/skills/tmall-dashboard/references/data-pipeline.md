## 两个飞书工作簿

| 用途 | 环境变量 | 内容 |
|---|---|---|
| 日报主表 | `FEISHU_WIKI_TOKEN` | 目标、日明细、投放、产品、流量 |
| 搜索关键词 | `FEISHU_WIKI_TOKEN_KEYWORDS` | 天猫 / 京东的搜索词与付费词长表 |

两份是完全独立的文档，所以两个 token。都挂在知识库里，读之前要先用 `resolveWikiNode()` 把 wiki token 换成 spreadsheet token。

飞书应用需要的**只读**权限：`wiki:wiki:readonly`、`sheets:spreadsheet:readonly`、`drive:drive:readonly`。光开权限不够，还得把应用**加进文档的协作者**，否则一律 `permission denied`。

## 主工作簿的六个页签

`lib/feishu/workbook.ts` 里的 `TAB_TITLES`：

| 常量 | 页签标题 | 读出什么 |
|---|---|---|
| `goals` | `1.目标达成` | 月度目标、月度实际（利润） |
| `overall` | `2.整体` | 日明细主干：GMV / 销量 / 退款 / UV / 投放消耗 |
| `insite` | `3.投放-站内` | 分触点日明细 + 站内汇总块 |
| `offsite` | `4.投放-站外` | 分渠道日明细 + 站外汇总块 |
| `traffic` | `6.流量` | 搜索 / 付费流量，拆到来源 |
| `productDetail` | `附-产品` | 分商品日明细 |

按**标题**定位，不按 sheet_id —— id 是工作簿内部生成的，表被复制或重建就会变；标题是人维护的，改了也能一眼看出来。

页签结构不统一，所以每块单独解析：`2.整体` 是「一行一天」，`1.目标达成` 是「一行一个指标、按月横向铺开」（转置了）。

### `3.投放-站内` / `4.投放-站外`

两部分：**分触点/渠道的日明细**（一行一天一触点）+ **汇总块**（表自己算好的每日合计）。

汇总块单独解析成 `adTotals`，因为站外的成交单数没法从渠道加总出来（没有这一列，且渠道级 CVR ≠ 汇总 CVR）。汇总块的列：站内是 GMV / 推广消耗 / 成交金额 / 成交单数 / ROI / 转化率 / 展现量 / 点击量，站外是推广消耗 / 成交金额 / ROI / 展现量 / 点击量 / CPM / CVR / CPC。

**日明细里的站内/站外消耗，和汇总块里的推广消耗，是两处独立维护的数** —— 实测逐日完全一致，可以互相当校验。

### `6.流量`

搜索 / 付费两组，各自有 UV、支付人数、支付金额，并拆到来源（手淘搜索、直通车…）。补进日报的 `searchUv` / `searchBuyers` / `searchGmv` / `paidUv` / `paidGmv`。

## 目标达成：两个区块

`1.目标达成` 这一页有两个独立的目标区块，**必须都读**：

### 左侧「月汇总 / 渠道目标」

一行一个月，**12 个月全在这儿**，外加 YTD / Q1 / Q2 / H1 汇总行。

列：`月份 | GMV | 主机销量 | 总费用 | 总费比 | 利润`（渠道目标组），后面还有「实际达成」组和「达成率」组。

只有 5 个指标，但覆盖全年。**季度和全年口径的目标全靠它** —— 只读右侧的话，「Q3 目标」会变成 7+8 月、「全年目标」变成 1–8 月。

解析时拿 YTD 行当**校验和**：12 个月加总必须等于 YTD 行，对不上就告警。

### 右侧「项目」区块

一行一个指标、按月横向铺开，每个月占 5 列（目标 / 实际 / 达成率 / 上月MTD / MTD环比）。月份表头在表头行的**上一行**。

15 个指标全在这儿（含站内外拆分、流量），但**只铺到当月**。

### 合并规则

先用左侧填满每个月，再让右侧覆盖上去。两边重合的月份数值一致（不一致会告警）—— 已知源表在 1/5/6 月的总投放费上矛盾，当前取右侧，因为它等于站内+站外、和拆分行自洽。

### 自洽补全

绝对值目标和率目标要互相自洽，缺哪边补哪边：

- `refund ??= refundRate × gmv`（表只给了退款率，页面上这行的主指标是绝对值）
- `searchBuyers ??= searchConversionRate × searchUv`
- `profitRate ??= grossProfit ÷ gmv`（月汇总只给了利润绝对值；不补的话 9–12 月的利润率整行是「—」）
- `adCostRate ??= adCost ÷ gmv`

### 未排目标的月份

站内外拆分和流量的分项没排到 9 月以后。`targetsForRange` 的规则：**区间里有任何一个月缺这项目标，整项作废（返回 null）**，页面显示「—」。

基数只数「有目标记录的月份」而不是日历月份 —— 否则全年周期跨 12 个月、表里只排到 8 月时，每一项都会作废，整张表变空。

## 搜索词长表

`lib/feishu/keywords.ts`。工作簿里有六个子表，只读 `raw-天猫搜索词` 和 `raw-天猫付费词`：

- `关键词汇总` 是按月 × 固定词桶的透视，做不了 Top N 排行
- `raw-京东关键词` 不在本看板口径内

天猫侧「搜索 + 付费」按 `(日期, 词)` 合并成一行 —— 同一个词既有自然曝光又被投放买过是常态，分开列会让同一个词在排行里出现两次。

两万多行，一次拉会超时，按 4000 行切块。

**词性判定** `classifyTerm()`：品牌优先，其次品类，其余归其他。品牌词的正则要收拼错的（`pluad` 一年 1244 个访客、`ploud` 752 个，全是冲着牌子来的）—— 留在「其他」里等于凭空削掉品牌词三千访客。判定顺序不能反，否则 `plaud录音笔` 会被划进品类。

页面侧用 CSR（压缩稀疏行）编码 5800 词 × 223 天的矩阵，否则 JSON 会爆。

## 解析的几条硬规矩

**按列名找列。** `col(grid, 'GMV')` 而不是 `row[2]`。表里插一列，所有列号全错位，而且不会报错 —— 只会安静地给出错误的数。同名列撞车时用 `colIn(grid, '分组名', '列名')`。

**认不出就跳过，不猜。** 日期解析不出来返回 null 然后跳过整行，不要用默认年份猜 —— 补错年份会让整份数据落到另一年，页面上表现为「全年累计是 0」，很难查。

**数值解析统一走 `num()`。** 它处理 `¥55,840`、`2.31%`（除以 100）、`-`、`#DIV/0!`、空。百分号不除以 100 的话费率会变成 231%。

**告警要具体。** `warnings.push()` 里写清楚是哪个月、哪个指标、两个值分别是多少、当前取了哪个。同步命令会把告警打出来，这是人发现源表出问题的唯一途径。

## 数据流的三段

```
lib/feishu/sync.ts        拉 + 解析 → DashboardSnapshot → data/snapshots/latest.json
lib/metrics.ts            聚合 / 达成 / 拆解（纯函数，不碰 IO）
scripts/payload.ts        拼成页面要的 DATA 形状（按列存的日序列 + 预算好的各板块数据）
```

`scripts/payload.ts` 被 `export-view.ts`（导出 JSON）和 `build-static.ts`（烤进 HTML）共用。两处各拼一遍的话，加了字段只改一处，静态站就会悄悄少一块数据。

`getSnapshot()` 的回落顺序：飞书（有凭据）→ 本地快照 → mock。`data/snapshots/latest.json` 在 .gitignore 里，所以 CI 上没有凭据就必然回落到 mock —— 这条分支是默认路径，不是边缘情况。
